## Context

See proposal.md - Why. This design currently covers only the interim manual workaround adopted on 2026-08-31 while the permanent automated fix is still being evaluated (see Open Questions). It will be revised once that evaluation lands on a chosen approach.

**2026-08-31, same day, ~3h after a validated-working bootstrap:** a routine health check (the loop described in Open Questions, run manually before it existed as code) found the cookie dead again — and not just the exported snapshot: `/refresh` itself returned `{"ok":false,"reason":"sessao_expirada_precisa_login_manual"}`, meaning the underlying persistent Playwright browser session had lost its login, not merely that the exported file was stale. This reframes the problem: it is not (only) "the exported snapshot rots faster than the persistent session," it may be that **the persistent session itself gets killed by Google within hours**, at least under the conditions seen today (the same account's session cookies were exported from the user's real browser and replayed into a VPS-hosted Playwright profile and separately into `yt-dlp`, twice, within the same few-hour window). That access pattern — one cookie generation used from several different client fingerprints/IPs in quick succession — is exactly the shape Google's session-hijacking heuristics are built to catch; a fast kill would be the expected response, not a bug. Not proven (n=1 day, could also be an unrelated account-level trigger), but it's the leading hypothesis now and changes what "the fix" needs to address — see Open Questions.

**2026-08-31, same day, third data point:** re-bootstrapped from a third fresh `cookies.txt` export (this time closer to zero delay between export and bootstrap+validation, per the "export hygiene" decision below) and the immediate `yt-dlp --simulate` succeeded again (`Downloading 1 format(s): 401+140`). Consistent with the working pattern seen the first time (bootstrap #2 earlier today): a fresh export, bootstrapped and validated with minimal delay, works. The open question is now purely about *how long this one survives* before the same hijacking-heuristic kill (if that's really the mechanism) hits it again — the monitoring loop is tracking that from here.

**2026-08-31, same day, fourth data point — died again, and this time the confound is smaller:** the monitoring loop's first scheduled health-check tick (an hourly `yt-dlp --simulate` probe, per this design's own interim process) found the session dead again — same signature (`WARNING: cookies ... rotated`, then bot-check `ERROR`), and `/refresh` again returned `sessao_expirada_precisa_login_manual` (persistent session itself dead, not just the snapshot). Unlike the earlier cycles, the time between the working bootstrap/validation and this failing check was mostly filled with **unrelated work in this session (an entire feature's implementation and deploy) that never touched the YouTube cookie at all** — the only thing that touched the session in between was, as far as can be reconstructed, this loop's own prior health-check tick(s). This sharpens (without yet resolving) the open question below: the death is not obviously caused by a burst of *human* multi-client activity (browser export + immediate use) the way the first incident looked — it's consistent with either (a) the hijacking-heuristic kill happening on a timescale of roughly 1-3h regardless of how many clients touch it, or (b) the monitoring loop's own hourly validation probe being enough "extra client touching the session" to itself trigger the kill it's trying to detect. These two are not distinguishable from this data point alone — see the sharpened test protocol in Open Questions.

## Goals / Non-Goals

**Goals:**
- Give the operator (human running a manual `/bootstrap`) a reliable way to know, before walking away, whether the cookie actually works — not just whether it looks logged-in.
- Keep the interim process cheap enough to run by hand every time, without needing the permanent fix first.

**Non-Goals:**
- Automating the end-to-end validation inside `cookie-refresher` itself (that's the permanent fix, still open — see Open Questions).
- Solving cookie rotation/staleness at the source (e.g. never letting the export go stale) — out of scope until the evaluation below picks a direction.

## Decisions

### Interim manual process: validate with a real `yt-dlp --simulate` probe after every bootstrap, not just the `/bootstrap` response

**Decision:** after any manual cookie bootstrap (`POST /bootstrap` with a freshly-exported `cookies.txt`), before considering the incident resolved, run a real `yt-dlp --simulate` against the video that originally failed (or any video, if none is on hand), using the freshly-written `/home/node/.n8n-files/youtube-cookies.master.txt`, from inside the `n8n-n8n-1` container:

```bash
docker exec n8n-n8n-1 sh -c '
  cp /home/node/.n8n-files/youtube-cookies.master.txt /tmp/test-cookies.txt
  chmod 600 /tmp/test-cookies.txt
  /home/node/.n8n-files/yt-dlp --no-playlist --cookies /tmp/test-cookies.txt \
    --js-runtimes node:/usr/local/bin/node --simulate \
    -f "bestvideo[height>=2160][ext=mp4]+bestaudio[ext=m4a]/best" \
    "https://www.youtube.com/watch?v=<VIDEO_ID>" 2>&1 | tail -30
  rm -f /tmp/test-cookies.txt
'
```

Only trust the fix once this prints a real format-selection line (e.g. `[info] ...: Downloading N format(s): ...`) with no `ERROR: ... Sign in to confirm` and no `WARNING: ... cookies are no longer valid`. A `{"ok":true,"cookieCount":N}` from `/bootstrap` alone is **not sufficient** — see proposal.md for why.

**Why this and not something else, for now:** it's the exact check that would have caught the 2026-08-31 incident (bootstrap #1 reported success but the real download still failed; only bootstrap #2, validated this way, actually worked). It requires no code change, so it's usable immediately while the permanent fix is still being evaluated.

**Alternatives considered:**
- Trusting `/bootstrap`'s own response — rejected, this is precisely the gap that caused the incident.
- Waiting for the next real ingestion run to reveal success/failure — rejected, too slow and too high-impact (a full run can be hours of wasted whisper.cpp/GPU-adjacent VPS time before the failure surfaces).

### Export hygiene: close other logged-in tabs/windows for the account before exporting `cookies.txt`

**Decision:** document (in the operational runbook) that the browser used to export `cookies.txt` should not be actively used for that YouTube account between export and hand-off, to reduce the chance the `SIDCC`-family cookies rotate before the file is even bootstrapped.

**Why:** the 2026-08-31 incident's working fix was a re-export done immediately, with no browsing in between; the first (failing) export had unknown but likely non-trivial delay/activity between export and use. Not proven causal, but consistent with known `SIDCC` rotation behavior and costs nothing to follow as a precaution.

## Risks / Trade-offs

- **[Risk] The manual validation step itself relies on a human remembering to run it.** → Mitigation: documented as a mandatory step in `cookie-refresher/deploy/README.md`, right after the existing bootstrap step, not as a separate/optional note.
- **[Risk] This interim process does nothing for unattended failures** — if the cookie silently goes stale between manual check-ins (the actual failure mode described in the proposal: "expires from one day to the next"), nobody notices until an ingestion run fails. → Mitigation: tracked as the monitoring loop in the parallel exploration effort (see Open Questions) — out of scope for this manual-process decision alone.
- **[Risk] `yt-dlp --simulate` still costs a real request to YouTube per validation** — could itself contribute to rate-limiting/suspicion on the account if run too often. → Mitigation: only run after a manual bootstrap (rare), not on a tight automated cadence, until the permanent design decides otherwise.

## Open Questions

- What should the permanent automated fix be? Candidates raised in proposal.md: (a) make `/refresh`/`/bootstrap` itself perform an end-to-end `yt-dlp` probe before reporting `ok:true`, (b) a separate continuous health-check loop that proactively detects staleness before an ingestion run hits it, (c) investigate whether the rotation can be avoided at the source. Being evaluated in parallel (self-paced exploration + monitoring loop), not blocking this interim decision. **Update 2026-08-31:** the Context finding above pushes weight toward (c)/root-cause first — if the persistent session itself is being killed by Google's hijacking heuristics rather than merely rotating, then (a)/(b) only ever *detect* the failure faster, they don't reduce how often it happens. A pure detection-only fix would still mean daily-or-faster manual re-logins forever.
- **New, higher-priority question:** does exporting the SAME account's cookies into more than one automated client (the persistent Playwright profile AND ad-hoc `yt-dlp --cookies` copies used for validation) accelerate the kill, independent of any real download traffic? If so, the interim manual-validation process in this very design.md (running `yt-dlp --simulate` from a *copy* of the master file, separate from the Playwright profile that `/refresh` maintains) could itself be contributing to burning sessions faster — worth testing by going a full day *without* any manual validation probe and seeing if the persistent profile survives longer than it did today. Tension to resolve: validation is what catches failures, but validation is itself session-touching traffic. **Update 2026-08-31 (4th data point):** the monitoring loop's own hourly `yt-dlp --simulate` tick is itself exactly this kind of extra-client traffic, and the session died on schedule with roughly only that loop touching it in between — consistent with, but not proof of, the loop being an accelerant. **Concrete next test, not yet run:** after the next bootstrap, run the monitoring loop in a mode that checks `/refresh` only (the Playwright-internal check, zero extra clients) for a full cycle, withholding the `yt-dlp --simulate` probe entirely, and compare how long the session survives against today's ~1h. If it survives noticeably longer, that confirms the validation probe itself is a meaningful accelerant and the interim process in this design's Decisions section needs to trade off "detect fast" against "don't be the cause."

**Test started, 2026-08-31 ~15:5X UTC (5th bootstrap):** fresh `cookies.txt` bootstrapped and validated working (`Downloading 1 format(s): 401+140`) immediately after. This is the baseline moment for the test above — the running monitoring loop is instructed to detect this fresh-bootstrap transition on its next tick and switch to an `/refresh`-only check (no `yt-dlp` probe) for one cycle, so the survival time can be compared against the ~1h seen when the loop's own probe was active.

**Test result, 2026-08-31 16:49:29 UTC — the accelerant hypothesis is disconfirmed, not confirmed.** The very next monitoring tick after bootstrap #5, running `/refresh`-only (zero `yt-dlp` probes since bootstrap, per the test protocol above — the only session-touching event in between was the one mandatory post-bootstrap validation call, which is unavoidable under this design's own interim process), found `/refresh` already returning `{"ok":false,"reason":"sessao_expirada_precisa_login_manual"}` — the persistent session was dead again, in roughly the same ~1h window as every prior cycle, **despite the extra probing being removed**. This is the cleanest data point so far and it points away from "our own validation traffic is killing the session" and back toward **a hard, short survival ceiling on this session regardless of how carefully it's used** — consistent with (but still not proof of) Google's anti-automation/session-hijacking detection reacting to the VPS environment itself (headless Chromium fingerprint, datacenter IP, or the export-then-replay-into-a-different-machine pattern inherent to this whole design) rather than to any particular access pattern this project controls. Reduces confidence in every mitigation candidate proposed so far that assumes the death rate is a function of *how* the session is used (a/b/c in the first Open Question, and the earlier "multiple clients" question) — none of them can fix a ceiling that exists regardless of usage pattern.

**Practical implication, worth surfacing to the user directly:** five bootstraps today, all following the documented interim process (fresh export, immediate use, no extra browsing), have each survived roughly 1-3h before dying again — never close to the "expires from one day to the next" originally described in the proposal. If this holds, the operational reality is closer to **needing a fresh manual cookie export multiple times per day**, not once a day, for as long as this account/environment combination is used this way. That is a much heavier manual burden than the original proposal anticipated, and no design change explored so far (detection speed, single-client validation, export hygiene) addresses the survival time itself — only how fast a death is noticed after it happens.
- Should the continuous monitoring loop (once designed) live inside `cookie-refresher` itself (e.g. an extra scheduled check alongside the existing daily cron) or as an external process? Deferred to that evaluation. **Update 2026-08-31:** if the "multiple clients touching one session" hypothesis holds, the monitoring loop should probably validate through the *same* Playwright-managed session `/refresh` already uses (one client only) rather than spinning up a separate `yt-dlp` probe against a copy — the interim process documented in Decisions above may need to change once this is confirmed.
- Is a single persistent browser session (however carefully isolated) fundamentally the wrong shape for an unattended, always-on pipeline — i.e. is there a ceiling on how long *any* automated replay of a real user's YouTube session can survive Google's anti-automation heuristics, meaning the real fix is organizational (e.g. a dedicated account/API path) rather than technical? Not resolved; flagging because today's data point is consistent with "no amount of engineering here buys more than hours-to-a-day," which would mean the whole `cookie-refresher` approach has a hard ceiling worth surfacing to the user explicitly before more design effort goes into it.

### Given the ceiling holds, what's actually worth building — three candidates evaluated

Reframing per the "practical implication" above: if survival time itself can't be fixed at this layer, the design question shifts from "how do we make the session live longer / detect death faster" to "given it dies every 1-3h regardless, what's the least painful way to live with that."

1. **Different execution environment (different IP/fingerprint) might survive longer — plausible but expensive to test properly, not recommended as a next step.** A residential-IP or different-network Chromium session might be treated less suspiciously than a VPS/datacenter IP, but testing this rigorously means running the exact same 5-bootstrap protocol from a genuinely different network, ideally in parallel with the current VPS session as a control — real infrastructure work (a residential proxy or a second machine), not a code change. **Not pursuing further in this design pass** — the cost of a proper test is disproportionate to what's known so far (a hunch, not even a partial data point), and even a positive result would only buy more hours, not eliminate the ceiling.
2. **YouTube Data API as a download path — ruled out, not worth further exploration.** The official YouTube Data API (the API this account could authenticate against without cookie replay at all) does not expose video *file* download — it's metadata/upload/playlist/comment management, not content retrieval. There is no API-key-based, ToS-compliant way to fetch the actual video bytes; every tool that does this (`yt-dlp` included) works by parsing the same player-response endpoints a browser uses, which is exactly the surface Google's anti-automation heuristics are watching. This candidate is a dead end for this pipeline's core need (downloading full videos), not a viable alternative to the cookie approach — worth recording so it isn't re-investigated later.
3. **Minimize human toil per re-bootstrap — SHIPPED 2026-08-31, see `openspec/changes/add-youtube-cookie-rebootstrap-ui`.** Closes this open question: the Admin can now re-bootstrap and get a real end-to-end validated result from Clip Studio's Configurações screen alone, no assisted SSH session needed. Confirmed working with a real re-bootstrap followed by a real YouTube submission processing successfully end-to-end. The candidate is described in full below for the historical record of how the decision was reached. Today's bootstrap procedure is a 3-step manual dance the human can't do alone: export `cookies.txt` from a browser, then a second party (this session, via SSH) has to `scp` it to the VPS, `docker cp` it into the `cookie-refresher` container, and `POST` it to `/bootstrap` with the right `wget --method=POST --body-file=...` incantation — documented in `cookie-refresher/deploy/README.md` §2 but not something the human can run unassisted. If re-bootstrapping needs to happen several times a day now, that dependency on an assisted multi-step process each time is the actual bottleneck, more than detection speed. A concrete, scoped fix: expose `cookie-refresher`'s `/bootstrap` endpoint through a route the human can hit directly and safely themselves (e.g. a tiny authenticated HTTP endpoint or a one-line script the human runs locally that does the `scp`+`docker cp`+`curl` in one shot), so re-bootstrapping stops requiring an assisted session every time. **This is the one candidate concrete enough to become a real proposal** — not designed further here (would need to pick a specific mechanism and think through exposing anything at all outside the internal network safely, given `youtube-cookie-auth`'s existing "Internal-only exposure" requirement), but it's the direction worth taking to the user next, rather than continuing to chase the survival-time question further.

**Mechanism refined with the user, 2026-08-31 (not yet formalized into its own change):** candidate 3 lands inside Clip Studio itself, not as a standalone script — `clipstudio-web-1` already sits on the `n8n_default` Docker network alongside `cookie-refresher-1` and `n8n-n8n-1` (see `VPS.md` §10), so an Admin-only addition to the existing Configurações screen (same screen as `N8nConfigForm.tsx`) can reach both internally, no new public exposure needed, resolving the "Internal-only exposure" tension cleanly. Flow agreed: (1) Admin pastes/uploads a fresh `cookies.txt` in Configurações; (2) Clip Studio's backend forwards it to `cookie-refresher-1:4600/bootstrap` over the internal network; (3) if that reports `ok:true`, Clip Studio backend calls a **new small n8n webhook workflow** (Execute Command node running the same `yt-dlp --simulate` probe already documented in this design's Decisions section — n8n already has `yt-dlp` installed, avoiding any need to expose the Docker socket to `clipstudio-web-1`) to get a real end-to-end validation result; (4) the screen shows one consolidated result ("✅ cookie válido e testado" or "❌ bootstrap ok, mas validação falhou: <motivo>"), same screen, no extra step. This was chosen over a bootstrap-only version (skip step 3, defer real validation to the next real download) specifically because the whole `harden-youtube-cookie-refresh-validation` change exists to close exactly the gap step 3 closes — a bootstrap-only self-service tool would reintroduce it. **Awaiting the user's explicit go-ahead to scaffold this as its own OpenSpec change** (a new n8n workflow change is a bigger unit of work than a pure Clip Studio change — worth a clean proposal of its own rather than folding into this one). Not yet started.
