## Why

The "Clip Studio — Integração N8N" ingestion workflow (`mfqp4D5HKs0MNhv1`) downloads YouTube videos via `yt-dlp` using a **read-only master cookie file** (`/home/node/.n8n-files/youtube-cookies.master.txt`, `chmod 400`, owned `node:node` — copied to a per-submission scratch file before each run so `yt-dlp`'s own cookie-jar rewrite behavior never corrupts the master) exported once, by hand, from a logged-in browser session and copied onto the VPS via SSH + `docker cp`. Confirmed live in production on 2026-08-27 (execution #602, a real submission through the Clip Studio UI): the master cookie had already gone stale and `yt-dlp` failed with `Sign in to confirm you're not a bot`, blocking the entire Uploader flow until someone notices and manually re-exports and re-copies a fresh cookie file. `clip-studio/deploy/README.md` also documents that `--extractor-args "youtube:player_client=android,web_safari"` was already tried on this exact VPS IP during initial setup and did **not** avoid the same bot-check — so that specific mitigation is not available here, not just untested. Research into current (2026) YouTube anti-bot behavior confirms the underlying pattern isn't a one-off either: YouTube rotates session cookies more aggressively for accounts exhibiting an automated usage pattern (repeated downloads from the same datacenter IP), regardless of whether the account is shared or dedicated, and no cookie-free alternative (PO Token providers, alternate `player_client` values, other open-source downloaders) reliably avoids the requirement for *some* valid session credential today. The realistic fix is not eliminating cookies, but eliminating the manual renewal step.

## What Changes

- New standalone Docker Compose service on the VPS, `cookie-refresher` (Playwright + Chromium, Node.js), joined to the same `n8n_default` network as the ingestion workflow, sharing the `n8n_files` volume so it writes directly to the existing master cookie path (`youtube-cookies.master.txt`), preserving its `node:node`/`400` ownership and the existing master/scratch-copy pattern already in the `Baixar Video YouTube` node unchanged.
- The service holds one **persistent, already-authenticated Chromium profile** (logged in manually, once, by the user — never automated) in its own dedicated volume. It never re-enters credentials; a refresh only re-visits `youtube.com` with the existing profile and re-exports the current session cookies in Netscape format.
- Exposes an internal HTTP endpoint (`POST /refresh`, no external route/DNS) that the ingestion workflow calls; also runs a daily preventive refresh via an internal cron so cookies rarely go stale between download attempts.
- If the persistent profile's own session has actually expired (not just close to rotating), the endpoint returns an explicit failure (`sessao_expirada_precisa_login_manual`) instead of attempting any form of automated login — automating login credentials was evaluated and rejected because it triggers Google's own anti-automation checks (CAPTCHA/2FA) on the login itself, trading one bot-detection problem for a worse one.
- **Modifies** the existing `Baixar Video YouTube` step in the "Clip Studio — Integração N8N" workflow: on the specific `Sign in to confirm you're not a bot` failure signature, it now calls `cookie-refresher`'s `/refresh` endpoint and retries the download exactly once before falling back to the existing error-callback path (which already exists and is unchanged) — turning a failure that previously required a human to notice and SSH in, into a self-healing retry in the common case.
- Does **not** add `--extractor-args "youtube:player_client=..."` — already tried on this VPS's IP (see Why) and confirmed not to help; not part of this change.

## Capabilities

### New Capabilities
- `clip-studio/youtube-cookie-auth`: automated, self-healing management of the YouTube session credential the ingestion pipeline's `yt-dlp` step depends on — covers the persistent-profile refresh mechanism, the preventive schedule, the reactive retry-on-failure behavior, and the explicit (non-automated) failure path when the underlying session is actually dead.

### Modified Capabilities
(none — `clip-studio/youtube-ingestion`'s spec, defined in the not-yet-archived `add-clip-studio-app` change, already describes "downloads it via yt-dlp" as the mechanism without specifying *how* the download authenticates; this change only changes that internal mechanism and adds a new capability around it, it does not change youtube-ingestion's own observable requirements)

## Impact

- **New infrastructure on the existing Contabo VPS**: one new Docker Compose service (`cookie-refresher`) + two new named volumes (the shared `n8n_files` mount, already existing, and a new `browser_profile` volume unique to this service) — no new external DNS/Caddy route, this is an internal-only service.
- **New one-time manual step required from the user**: logging into the dedicated Chromium profile once (via a temporary SSH tunnel/VNC or by transferring an already-logged-in profile) before the service can do anything — this cannot be automated by design (see Why/What Changes).
- **Modified**: the `Baixar Video YouTube` Execute Command node in workflow `mfqp4D5HKs0MNhv1`, adding the retry-with-refresh logic on top of its existing master/scratch cookie handling (unchanged otherwise). No changes to the "Blocos" pipeline (`ID4wisnN4Tqpt2zh`) or to any other Clip Studio capability.
- **Operational**: introduces a new maintenance surface (the persistent browser profile can still eventually need a real manual re-login when Google fully invalidates the underlying session, expected to be much rarer than the current per-download cookie expiry) — documented as an explicit, rare, human-in-the-loop fallback rather than eliminated entirely.
