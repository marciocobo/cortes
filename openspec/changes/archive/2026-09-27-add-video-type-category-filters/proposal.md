## Why

Hoje a biblioteca de vídeos só filtra clipes por status de produção (`Original`/`Cortado`/`Processando`) — não há como restringir a grade pelo tipo de conteúdo do clipe (Pregação, Podcast, e em breve Louvor). Conforme o número de clipes entre pipelines cresce, encontrar um clipe específico significa rolar a grade inteira já filtrada por status. Um mockup revisado (fornecido pelo usuário) adiciona um filtro "Tipo" (tipo de conteúdo) acima do filtro de status já existente — este último relabelado "Categoria" — para que um Clipador restrinja primeiro por tipo de conteúdo, depois por status. O mockup também prepara um terceiro tipo de conteúdo, **Louvor**, no filtro "Tipo" da biblioteca e no badge do clipe, mesmo que o próprio formulário "Enviar Vídeo" do mockup deliberadamente não ofereça Louvor como opção de envio — ainda não existe nenhum pipeline n8n que produza clipes de Louvor. Esta change traz a UI de filtragem/classificação da biblioteca em linha com o mockup e reserva o modelo de dados (`SubmissionMode`, convenção de pasta no OneDrive) para Louvor, para que uma change futura consiga ligar o pipeline real de geração de cortes sem precisar de migração de schema.

## What Changes

- Adiciona uma linha de filtro **Tipo** (tipo de conteúdo) na biblioteca de vídeos, acima do filtro de status já existente: pills para `Pregação`, `Louvor`, `Podcast`. Ao abrir a biblioteca de vídeos agora é necessário escolher um Tipo primeiro — bate com o "Selecione um tipo para ver os vídeos." do mockup, uma mudança de UX **BREAKING** em relação ao comportamento atual (a biblioteca hoje mostra clipes com status `Original` imediatamente, sem exigir seleção de tipo).
- Relabela o cabeçalho da linha de filtro de status (hoje sem rótulo explícito) para **Categoria**, e desabilita suas pills (com tooltip "Selecione um tipo primeiro") até que um Tipo seja selecionado — bate com o mockup.
- Substitui as pills separadas `Palavra Completa`/`Podcast` de cada card de clipe por um único badge de tipo de conteúdo (`Pregação`/`Louvor`/`Podcast`, colorido conforme o mockup), mantendo o badge `Palavra Completa` já existente ao lado dele para clipes de Pregação produzidos por aquele pipeline (os dados de demonstração simplificados do mockup não modelam essa distinção de formato, mas o app real precisa dela — ver design.md).
- Classifica o tipo de conteúdo de cada clipe a partir da mesma convenção de marcação `sourceFolder` já usada para `isFullWord`/`isPodcast` (`Videos-Cortes/Cortes` e `Videos-Cortes/PalavraCompleta/Cortes` → Pregação, `Videos-Cortes/Podcast/Cortes` → Podcast), e reserva uma nova convenção `Videos-Cortes/Louvor/Cortes` para Louvor — nenhum clipe será classificado como Louvor até que um pipeline futuro grave ali.
- Adiciona `LOUVOR` ao enum `SubmissionMode` (só a nível de schema) para que um futuro pipeline/caminho de envio de Louvor não exija outra migração. O formulário "Enviar Vídeo" e os webhooks de envio continuam oferecendo só `Pregação`/`Podcast`, batendo com o mockup — nenhum pipeline de geração de cortes para Louvor é construído nesta change.
- **Pequeno ajuste, achado na validação completa do mockup**: o cartão de usuário no rodapé do sidebar mostra o papel humanizado ("Clipador"/"Uploader"/"Admin", conforme o `roleLabel` do mockup) em vez do valor cru do enum Prisma ("CLIPADOR"/"UPLOADER"/"ADMIN") exibido hoje.

## Impact

- **Código**: `src/app/(dashboard)/videos/VideoLibrary.tsx` (novo filtro Tipo, bloqueio de Categoria, renderização do badge), `src/lib/n8n-client.ts` (`ClipSummary` ganha um campo `contentType` derivado de `sourceFolder`, substituindo o par de booleanos `isFullWord`/`isPodcast` como fonte da classificação de tipo, mantendo `isFullWord` para o badge de formato), `prisma/schema.prisma` (enum `SubmissionMode` ganha `LOUVOR`, ainda sem uso por nenhum caminho de envio), `src/app/(dashboard)/enviar/SubmissionHistory.tsx` (mapa `CONTENT_TYPE_LABEL` ampliado por completude de tipos, inalcançável até existirem envios de Louvor), `src/app/(dashboard)/Sidebar.tsx` (rótulo de papel humanizado no cartão de usuário).
- **Dados**: uma migração Prisma adicionando o novo valor de enum `LOUVOR`; nenhuma outra mudança de schema.
- **Fora do escopo**: nenhum workflow n8n para geração de cortes de Louvor, nenhuma pasta `Videos-Cortes/Louvor` criada no OneDrive, nenhuma opção "Louvor" no formulário "Enviar Vídeo" nem nos webhooks de ingestão — tudo reservado para uma change futura.

## Achados adicionais na validação completa do mockup (NÃO resolvidos nesta change)

A validação linha a linha do mockup revelou dois pontos onde o comportamento hoje em produção diverge do que `openspec/specs/clip-studio/auth-rbac/spec.md` já documenta — o mockup, sem que isso pareça intencional da parte do usuário (o pedido original só mencionou tipo/categoria/Louvor), reflete o comportamento que o *spec* descreve, não o comportamento que o *código* atual implementa. São mudanças de controle de acesso (RBAC), com risco e blast radius reais o bastante para não serem resolvidas silenciosamente dentro desta change — ficam aqui documentadas para uma decisão explícita antes de virarem uma change própria:

1. **Biblioteca de vídeos sem escopo por dono.** O spec diz, na Scenario "Admin permissions": "the video library and submission history show every user's videos/submissions, **not just the Admin's own**" — por contraste, isso implica que um Clipador deveria ver só os próprios vídeos. Mas `GET /api/clips` (`src/app/api/clips/route.ts` → `listClips()`) não filtra por dono nenhum: todo Clipador autenticado já vê os clipes de qualquer um hoje. O mockup reintroduz esse filtro (`scopedVideos = isAdmin ? videos : videos.filter(v => v.ownerId === session.id)`, e `showOwner: isAdmin` no card). **Risco se implementado sem cuidado**: `submittedByName` (o mecanismo de atribuição de dono já existente) é `null` para qualquer clipe cujo vídeo original não foi enviado pelo próprio Clip Studio (ex: solto manualmente no OneDrive) — filtrar por dono estrito poderia esconder da maioria dos Clipadores a maior parte dos clipes já existentes.
2. **Clipador sem acesso a "Enviar Vídeo".** O spec diz, na Scenario "Clipador permissions": um Clipador "grants access to the video library (...) **and the YouTube submission flow**". Mas `CAPABILITY_ROLES.youtubeIngestion` em `src/lib/rbac.ts` (com um comentário citando explicitamente este mesmo spec) e `Sidebar.tsx`'s `ALL_LINKS` restringem `/enviar` a `UPLOADER`/`ADMIN` só — Clipador é excluído, tanto na UI quanto no servidor. O mockup segue essa mesma restrição do spec (`isUploader = role==='uploader' || role==='clipador' || isAdmin`).

Não está claro qual lado (spec ou código) está desatualizado em cada um dos dois casos — pode ser um spec nunca sincronizado após uma decisão de produto, ou um código que diverge por engano. Recomenda-se uma decisão explícita do usuário antes de tratar qualquer um dos dois, em uma change separada.
